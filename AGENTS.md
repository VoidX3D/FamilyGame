# AGENTS.md

Working notes for any AI agent, or any new contributor, picking up this
repository. It is short on purpose: if a rule is not in here, it is probably
not a rule.

If you want the shared memory of the project (what is deployed, what is
finished, what is next, and why things are the way they are), read
[`.agents/`](.agents/README.md) as well.

---

## 1. What this project is

**Family Game Hub** is a private, browser-based party-game hub for **3 to 10
people in the same room**. One host creates a room and gets a five-character
code; everyone else joins from a phone with that code; the host starts a game.

There is no account, no database and no social graph. Rooms are private and
short-lived. Everything that happens during a game travels over Socket.IO, not
over REST.

The thirteen games in the catalogue:

| Id | Name | How a round works |
| --- | --- | --- |
| `one-of-us` | One of Us | Crew vs imposter. Clues are spoken out loud. The room votes by itself. |
| `draw-it` | Draw It | One drawer draws a secret word on a server-owned clock; the room guesses. |
| `who-is-it` | Who Is It? | Everyone votes for another player; the most-voted player(s) score. |
| `who-am-i` | Who Am I? | Each player gets a different person; they see everyone else's, never their own. |
| `where-am-i` | Where Am I? | The same, with places. |
| `who-wrote-that` | Who Wrote That?! | Answers are anonymous; players match them to authors. |
| `act-it-out` | Act It Out | One actor acts a prompt and taps the first correct guesser. |
| `truth-or-dare` | Truth or Dare | Everyone submits a truth and a dare; the pool is dealt into turns. |
| `caption-this` | Caption This | Everyone writes a caption; the room votes anonymously. |
| `emoji-guess` | Emoji Guess | Decode an emoji clue; first correct guesses score more. |
| `spyfall` | Spyfall | Everyone gets a location except the spy; the room votes. |
| `would-you-rather` | Would You Rather? | Pick one of two options and optionally explain why. |
| `two-truths-one-lie` | Two Truths & One Lie | Submit three statements; the room guesses the lie. |

**Draw It has three rules that are easy to break by accident:**

1. **The drawer cannot end the turn.** There is no "done" action and no
   button. The clock is the only thing that ends a turn. If the drawer can
   end the turn, the drawer can also decide when the word becomes visible,
   and the whole game is worthless.
2. **A player may guess as often as they like.** A wrong guess must not
   lock a player out of the next one.
3. **The word is not in the guess list.** A correct guess is shown as
   "got it!", never as the word itself. The close-guess hint shows the
   letters that landed in the right place, which can never spell the whole
   word, because a guess that matched every position would have been a
   correct guess.

## 2. The stack

| Layer | Choice |
| --- | --- |
| Runtime | Node.js 18 or newer |
| Server | Express 5 + Socket.IO 4 |
| Front end | Vanilla ES modules, plain HTML and CSS |
| Build step | **None.** The browser loads the source files directly. |
| Third-party front-end code | Vendored in `web/vendor/`: GSAP, Lenis, Socket.IO client |
| Storage | Rooms in server memory; a JSON content bank on disk |
| Database | None, and none is planned |

`web/vendor/` is filled by `npm run vendor` (see `scripts/vendor.mjs`). The
licences for the vendored builds are in `web/vendor/THIRD-PARTY.md`.

The icons are [Lucide](https://lucide.dev/) (ISC). `npm run icons` copies the
`.svg` files the app uses into `web/assets/icons/` and regenerates
`web/icons.js` from them. **Do not hand-edit `web/icons.js`** — it is
generated, and it says so at the top. Add the icon to the list in
`scripts/build-icons.mjs` and run the script.

`web/sitemap.xml` and `web/robots.txt` are generated by `npm run sitemap`
from `web/manus-routes.json`, which is the one list of the site's pages.

**Never write down a host or a port anywhere else.** `web/endpoints.js`
is the one file that says where the API, the preview and the deployed
sites are, and it has no DOM in it, so the browser, the dev server, the
test driver and the scripts all read the same numbers. `web/config.js`
decides which address to use and exports it; `web/net.js` imports the
answer and has no host in it at all. The backend keeps its own list of
allowed frontends, because the `backend` branch is a split of `server/`
alone and cannot reach `web/endpoints.js`; the CORS suite checks that the
two lists agree.

There is no bundler, no transpiler, no framework and no CSS pipeline. A file
the browser needs is a file the server has to serve.

## 3. The rules of the house

These are the rules that matter. Breaking one of them is a bug even when the
code looks fine.

### 3.1 The server is the only authority

An unrevealed secret — a word, a person, a place, a role, a prompt — must
**never** appear in `publicView()` and must **never** appear in another
player's `playerView()`. It may appear:

- in the `playerView()` of the player it belongs to,
- in the `publicView()` **after** the reveal phase has started,
- in server memory, obviously.

The host console gets `adminView()`, which carries controls and submission
counts, not the secret.

The test suites check this. `scripts/smoke-engines.mjs` stringifies the
public view and asserts that the secret is not in it; `scripts/smoke-games.mjs`
plays real games over a socket and checks the same thing from the wire. If
you add a game, add that check for your game.

### 3.2 The browser is never asked to decide anything the server can decide

Guesses are checked on the server. The client sends the text; the server
compares it (case, punctuation and spaces ignored) and answers correct or
not. The client does not hold the answer and does not compare anything.

The same goes for votes, scores, turn order and clock deadlines. If you find
yourself writing a comparison in `web/games.js`, move it to the engine.

### 3.3 The game state is a snapshot; the client renders it

The server publishes state; the client renders it. It is not a diff protocol
and it is not a command stream.

`paint()` in `web/games.js` builds the next screen in a detached node and
compares `stage.innerHTML` with `root.innerHTML`. If they are equal, the DOM
is left alone. That is deliberate: a state broadcast must not wipe what
somebody is typing, and must not steal focus.

**The Draw It canvas is the one exception.** It is a single persistent node
that is *moved* into place and never rebuilt, because a fresh `<canvas>`
element comes up blank. If you touch the drawing code, keep that property.

### 3.4 The dark theme stays dark

There is no theme switcher and no light mode. Colours live in the `:root`
block at the top of `web/styles.css`; use the variables (`--bg`, `--surface`,
`--primary`, `--on-surface-muted`, `--border-soft`, `--radius-md`,
`--space-*`, `--ease-emphasized`, `--font-sans`, …) instead of writing hex
values into new rules. Hard-coded colours in new CSS are a smell.

### 3.5 Keep the source header

Every source file starts with:

```js
/* Made by VoidX3D (Sincere Bhattarai) - Family Game Hub */
```

Keep it on new files too. It is the only attribution in the code.

### 3.6 No new dependencies without a reason

There is no bundler, so a dependency is not just `npm install`: the file has
to be **served** or **vendored** into `web/vendor/`. Before adding one, ask:

1. Is it small enough to write ourselves in twenty lines?
2. Can it be vendored, and does its licence allow it?
3. Does it need a build step?

If the answer to all three is no, it does not go in.

### 3.7 Do not rewrite `web/admin.js` or `web/games.js` wholesale

Both are large (75 KB and 74 KB) and both work. Change them **in place**.
A full-file rewrite loses the small decisions that are already in there:
the focus restore, the draft keys, the redaction, the canvas reuse, the
in-flight guards. If a file has become genuinely unmanageable, split it —
do not reformat and rewrite it.

### 3.8 Comments explain why, not what

The code already says what it does. A comment earns its place when it records
a rule, a trap or a decision ("the server owns the clock, so a phone that
sleeps can never end a turn").

## 4. Branches and deployment

| Branch | What it is | Where it goes |
| --- | --- | --- |
| `main` | The source of truth. Front end in `web/`, backend in `server/`. | Vercel builds the front end from it. |
| `backend` | **Generated.** A subtree split of `server/` on its own history. | The hosting panel pulls it and runs the API. |

`backend` is an **output**, not a working branch:

- It is published by `.github/workflows/sync-backend.yml` (a `git subtree
  split --prefix=server HEAD`, then a normal push on top of the previous
  tip).
- It is **force-published** in the sense that the workflow refuses to
  continue if the tree contains anything from `web/` or `.github/`, and the
  branch is always a straight line so every clone can fast-forward.
- It must **never** be merged into another branch. Git cannot reconcile the
  two histories, and a merge attempt leaves the repo in a state where neither
  side can be trusted.
- `git config pull.ff only` is set, so a pull **refuses** a non-fast-forward
  instead of silently creating a surprise merge commit.

If a pull on the hosting machine complains, run:

```bash
npm run deploy:update
```

`scripts/sync-backend.mjs` fetches `origin/backend`, force-points the local
`backend` branch at it, and stashes any local edits on that branch instead of
discarding them.

The workflow runs `npm run smoke` **before** it publishes. A failing suite
therefore stops the backend from being deployed at all, which is why the
suites check invariants rather than a fixed list.

## 5. Running it locally

```bash
npm install
npm --prefix server install
cp server/.env.example server/.env
```

Edit `server/.env` and set `ADMIN_PASSCODE` (at least 12 characters). If you
leave it out, the server generates one, keeps it in
`server/data/admin-passcode` and prints it on startup. `npm run passcode`
prints the passcode in use.

Then two terminals:

```bash
npm run dev:server   # the API on http://localhost:12800
npm run dev:web      # the front end on http://localhost:5173
```

| URL | What |
| --- | --- |
| <http://localhost:5173/> | Player shell |
| <http://localhost:5173/admin> | Host console |
| <http://localhost:5173/g/CODE> | Short invite link |
| <http://localhost:12800/api/docs> | API documentation |
| <http://localhost:12800/healthz> | Health, uptime, rooms, content status |

The port is **12800** everywhere — the API, `web/config.js`, `web/net.js`,
the test driver and the dev server CSP all point at it. The hosting service
requires that port.

## 6. The tests

| Command | What it covers |
| --- | --- |
| `npm run smoke` | All six server suites, in order. |
| `npm run smoke:server` | The HTTP API is up and answers. |
| `npm run smoke:cors` | Only the configured frontends may talk to the API. |
| `npm run smoke:config` | The server works with no configuration, and the passcode survives a restart. |
| `npm run smoke:foundation` | Auth, rooms, sockets, reconnect, lock, reset. |
| `npm run smoke:engines` | Every game engine driven to completion, including the secret-leak checks. |
| `npm run smoke:games` | A real Socket.IO play-through of all thirteen games. |
| `npm run smoke:ui` | Login, routes, invite links, lobby, layout, reset, 404. |
| `npm run smoke:game-ui` | A full One of Us game, host controls, lock, all viewports. |
| `npm run smoke:ui-all` | All active games end-to-end in Chrome. |

The three browser suites need **both dev servers running** and **Chrome**.
They read `ADMIN_PASSCODE` from the environment, from `server/.env` or from
the generated `server/data/admin-passcode`. Screenshots land in `.shots/`
(gitignored). `WEB_URL`, `API_URL` and `SCREENSHOT_DIR` override the
defaults.

**The suites check invariants, not a snapshot of the game count.** They assert
that the core games are present, that ids are unique, that every game
exports its seven functions, that every active game has a client screen and that
every content collection has entries. The browser suites compare the card
count with the API catalogue instead of a hard-coded number.

Keep it that way. Adding a game must not break a suite, and a suite must not
have to be edited when a game is added.

## 8. Adding a game

A game is **one file** in `server/games/`. Copy the shape of an existing
engine rather than inventing a new one.

1. **The engine** (`server/games/yourGame.js`) exports `meta` and seven
   functions:

   | Export | What it does |
   | --- | --- |
   | `meta` | `id`, `name`, `tagline`, `minPlayers`, `maxPlayers`, `maxRounds`, `hasScore`. |
   | `create(room)` | Builds the initial game state. Use `gameState(meta, room)` from `common.js`. |
   | `action(room, game, playerId, payload)` | Handles a player action. Returns `{ ok: true }` or `{ ok: false, error }`. |
   | `adminAction(room, game, type)` | Handles a host control. |
   | `nextRound(room, game)` | Advances to the next round, or ends the game. |
   | `publicView(game, room)` | What everybody sees. **No secrets.** |
   | `playerView(game, playerId)` | What one player sees. May contain their own secret. |
   | `adminView(game, room)` | What the host console sees. Counts and controls, no secrets. |

   Start the view from `publicBase(game)` so the shape stays the same for
   every game.

2. **The registry**: add the engine to the `engines` array in
   `server/games/index.js`. That is all — `GAMES`, `GAME_LIST` and
   `getGame()` are derived from it.

3. **The content**: add a collection to `server/data/content-schema.json`
   and the entries to the appropriate `server/data/games/<game-id>.json` bundle. If the collection
   has a built-in fallback, the game still starts when the collection is
   empty or missing.

4. **The client**: add a renderer to the `RENDERERS` map in `web/games.js`.
   The key is the game id. A game with no renderer shows "This game screen is
   not available yet." on a phone, which looks broken.

5. **The tests**: add the game to the play-through in
   `scripts/smoke-games.mjs`, and add a secret-leak check to
   `scripts/smoke-engines.mjs`. The suites assert invariants, so you do not
   need to touch the counts.

## 9. Content is data, not code

The words, questions, people, places, prompts and dares live in
`server/data/games/*.json`. The shape of each collection lives in
`server/data/content-schema.json`.

Adding content is a JSON edit, not a code change. Adding a *new kind* of
collection is a JSON edit in the schema plus entries in the game content bundle.
The host console reads the collections from `GET /api/admin/content` and
saves with `PUT /api/admin/content/:key`; the server validates the whole
collection and writes the file atomically.

A collection that is registered but missing from the game content bundle must not
take the server down. It is reported and the game falls back to its own
fallback entry.

Content changes apply to future rounds and turns. A game that is already
running keeps the prompts it has already assigned.

## 10. The API documentation

| URL | What |
| --- | --- |
| `/api/docs` | The real Swagger UI, served by the backend from `swagger-ui-dist`, with a dark theme that matches the app. |
| `/api/openapi.json` | The machine-readable description. It can be dropped into Swagger UI, Postman or a code generator. |

`GET /healthz` is public on purpose: it reports the version, the uptime, the
number of open rooms and players, the content status, the allowed frontends
and the memory the process is using, so a monitor can watch it.

Everything that happens **during** a game travels over Socket.IO, and those
events are listed at the bottom of the docs page.

## 10. Content and future migration boundaries

Built-in defaults are split into one bundle per game under
`server/data/games/`. Each bundle has a `gameId` and a `collections` object;
`truth-or-dare.json` is the example of one game owning two collections. The
runtime still exposes collections through `contentStore.js`, and host edits
still persist to `server/data/content.json`. `server/data/default-content.json`
is a read-only compatibility copy for staged backend upgrades; new content
must be added to the split bundle, not the legacy file.

The database migration and page-first visual direction are documented in
[`docs/CONTENT-AND-DESIGN-ROADMAP.md`](docs/CONTENT-AND-DESIGN-ROADMAP.md).
Neither is enabled by this repository state. Do not add a database dependency
or redesign the card-based UI until the open product decisions in that roadmap
are answered.
